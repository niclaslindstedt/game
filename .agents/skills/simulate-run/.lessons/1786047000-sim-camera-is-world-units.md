---
title: The sim's camera is WORLD units, not canvas px — and A/B a camera change with --view, never with an edit
date: 2026-08-09
scope: engine/sim/simulate.ts
concepts: [camera, view, units, ab-testing, measurement]
---

**`SIM_VIEW_DEFAULT` is a WORLD rect and the canvas number is a quarter
shorter.** The reference device is a ~844×390 CSS viewport, which at
`VIEW_SCALE` 2 is a **422×195 CANVAS** — but the ground plane is pitched
(`DEFAULT_PITCH` 0.75), so that canvas shows **422×260 WORLD units** of floor.
The app never stamps the canvas size into the input: `GameScreen.tsx` stamps
`worldViewRect(canvas.w, canvas.h)`, and every engine read of a view rect
(`sight.ts` `visibleTo`, the spawners' `summonGeometry`, the bot's
`knownSightFrom`) compares it against world positions. The constant read
422×195 for a while, so every simulated run watched through a camera 25%
shorter than any real player's and read every view-gated rule low.

The three call paths, if you ever need to re-confirm the unit:

- **App** — `GameScreen.tsx` `simulate()`: `worldViewRect(canvas.width,
  canvas.height)` offset by the camera. World units, and the comment above it
  says so.
- **Session server** — no rect of its own. The client sends its whole
  `GameInput` up (`server/client.ts` `sendInput`), `applyInput`
  (`session-model.ts`) spreads it onto the seat's live input, so the server
  inherits the app's units. `view` is in `UNSENT_FIELDS`/`PRIVATE_PLAYER_FIELDS`
  going the other way — snapshots never carry it.
- **Sim** — `simCamera()` clamps the rect to `state.level.width/height`, which
  are world units. That clamp is itself the proof the input must be world-space.

**A/B A CAMERA CHANGE WITH `--view`, NOT WITH TWO CODE STATES.** `--view WxH`
takes exactly the rect the constant supplies, so `--view 422x195` vs
`--view 422x260` measures the change with one tree, one build and one content
generation. That matters more than usual here: catalogs are regenerated by
anything running `make levels`, and a sweep that starts after one finishes is
comparing content as well as camera. **Launch both sides CONCURRENTLY** — each
process reads the generated modules once at startup, so two started in the same
second are pinned to the same catalogs whatever happens to disk afterwards.
(Measured: the generated hash moved twice during one 15-run sweep.)

**What the taller camera moved** (medium→jesus critical path, 2 seeds):

- The clean number is **RUN 1 of the sweep** — same starting hero, same carve,
  no divergence yet. Both seeds read **kills/min +22%** (23.1→28.1 and
  18.6→22.6) and dpsOut +13–25%. That is the honest size of the effect.
- Everything downstream of run 1 is chaotic and disagreed between seeds:
  campaign kills +33% on one seed and −2% on the other, because the two sides
  fall into different weapon chains within a rung or two. **Do not quote a
  campaign total as the effect of a camera change.**
- Consistent across both seeds: **deaths down** (316→89, 188→152), **bosses
  engaged-but-not-felled down** (9→3, 17→8) — the hero can now see and finish
  what he used to stall against — and **equipment drops up** (+55%, +11%) with
  the gated share up with them.
- Also consistent and worth a look: the **stuck penalty rose** on both seeds
  (66→99, 43→68) even though the bot's wall sense reaches further. Not
  investigated here.

The `--verdict` line was already FAIL on both sides (loot-fits-level, DPS on
curve), so it is useless as an A/B gate on a change this size — read the per-run
table.
